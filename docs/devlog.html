Phase 3.2 — the approval queue

The part that makes an escalation actually pause-and-wait instead of just halting. A new graph node packages the full context — task, plan, completed steps, the step awaiting a decision, the agent's proposed action — and pushes it to Postgres, the first real use of Postgres in this project (working memory lives in Redis, long-term memory in Chroma, deliberately). Resuming didn't need LangGraph's checkpointer machinery: everything needed to keep going already lives in the graph's own state, so resuming just means reconstructing that state, folding in the human's decision, and calling the graph again.

Three decisions, two shapes. Step-level escalations support approve (output accepted as-is), reject (sent back for another attempt with the reviewer's feedback — the same channel automated rejections already use), and modify (the reviewer's edited output accepted instead). Plan-level escalations only support approve (run the plan) or reject (the task ends outright — nothing partial to retry); modify is rejected with a clear error rather than faking a whole edited plan. Two review surfaces — a CLI and a Streamlit dashboard — share the same decide-then-resume path underneath. 104/104 tests passing.

Phase 3.1 — escalation triggers

Started Phase 3 (Human-in-the-Loop) by defining, in one place, every condition that sends a task to a human. Low plan confidence — the supervisor now self-reports a confidence score on the whole plan, checked before any specialist runs. Sensitive operation — a plan step's own text gets keyword-matched for financial transactions, data deletion, or external communication, deliberately not asked of the model. Specialist failed twice — tightened from a 3rd attempt to a 2nd. Low quality score — the reviewer's existing low-confidence trigger, renamed to match. User requested — a new flag on the incoming task forces escalation regardless of how confident anything downstream is. All five route through the existing escalation path; the plan-level ones now short-circuit before a single specialist dispatches, not just after one fails. 90/90 tests passing.

Phase 2.4 — memory management

Long-term memory now has upkeep instead of just growing forever. Records carry a user_id (a new concept — nothing tracked "who" before this), an access count, and a last-accessed timestamp. Importance blends access frequency with recency decay and re-ranks retrieval, so a frequently-useful memory can beat a barely-more-relevant one nobody's touched again. Expiration deletes memories that are both old and rarely accessed. Consolidation clusters near-duplicate same-outcome memories per user and merges them into one summary via a structured LLM call. A Streamlit dashboard shows what's remembered about a user, with buttons to consolidate or delete; a companion script gives the same deletion path as a CLI — the "delete endpoint" for a data request, honestly scoped to a project with no HTTP server yet. 79/79 tests passing.

Phase 2.3 — memory retrieval feeds planning

Memory records now capture the outcome (succeeded or escalated) and the plan steps used, not just prose. MemoryWriterAgent now runs on escalated tasks too, not just successful ones, so failed approaches get remembered as "don't do this again" instead of just dropped. The supervisor's planning prompt shows retrieved memories with their outcome, past plan, and any facts or preferences, so a new plan can lean on what worked and avoid what didn't. Escalated tasks still skip delivery, so their working memory survives in Redis for a human to inspect. 65/65 tests passing.

New direction

What Orchestra is actually for

Decided to stop being a generic orchestration demo and aim at a concrete use case: a research assistant for faculty — triage newly published papers in a field, summarize methodology, and flag contradictions against a professor's current findings, escalating uncertain or conflicting results to a human instead of guessing. The orchestration core stays domain-agnostic; this becomes the flagship application built on top of it, not a rewrite. No real lab data gets ingested.

Phase 1.1 — the supervisor / specialist / reviewer hierarchy

Modeled the three-layer agent hierarchy as LangGraph nodes. The Supervisor turns a raw task into a JSON execution plan, delegates one step at a time, and synthesizes the final answer once every step is approved. Four Specialists (research, data analysis, writing, code execution) share one base class with domain-specific prompts — tool binding is stubbed for now, that's a separate ticket. The Reviewer validates each specialist's output and, on rejection, loops it back to the same specialist with feedback attached, up to two retries before flagging needs_escalation — a placeholder hook for the human-in-the-loop system in Phase 3.

  • All state flows through one shared OrchestraState, typed with Pydantic schemas (ExecutionPlan, SpecialistResult, ReviewVerdict).
  • Routing between nodes is two small conditional-edge functions keyed off status and the current step's domain.
  • 8 structural tests pass with no API key needed — the reviewer's LLM call is mocked.
  • Haven't done a live end-to-end run yet — next step, once a key is in .env.
